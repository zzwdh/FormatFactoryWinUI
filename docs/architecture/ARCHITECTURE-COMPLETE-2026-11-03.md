### 压缩包会话

执行、恢复、保存、取消、收据与历史补录已移入 `ArchiveSession`。页面包装同一任务模型，首次恢复、关闭和保存共享恢复屏障。成功检查点未保存时保留已发布产物和提交收据；历史补录失败不撤销成功状态，下次恢复继续补录。密码不进入检查点、收据或历史，恢复后重新请求密码。详细故障顺序及首轮测试见原报告。

共享的文件指纹与临时 IO 失败分类分别由 `FileFingerprintService` 和 `ConversionFailurePolicy` 提供，普通转换与队列不再借用自动化编排类的静态工具方法。

### 主队列状态和操作

`QueueSession` 继续拥有真实任务、调度准入、保存、恢复、分组排序约束和撤销保留。`QueueOperationsCoordinator` 提供开始、重试、暂停、删除分类、批量编辑范围和格式交集、优先执行等命令协调；它通过会话完成持久化事务，不直接修改控件。

`QueuePageViewModel` 持有任务展示集合及可见集合、筛选、选中身份、摘要、任务栏展示数据与批次结果。新增包装项始终引用会话的同一个 `MediaTask`；筛选和排序保持展示项身份，不以重建任务实现刷新。命令入口从当前控件选择同步身份，避免延后的选择事件影响批量操作。

后台进度由 `PublishProgress` 按任务引用和执行代次合并，旧执行的回调不能覆盖新执行的待处理进度。该方法只写受锁保护的快照；宿主 200 ms 计时器在 UI 上下文调用 `DrainProgress`，再更新绑定对象、通知和任务栏。删除、结束和释放时清除相应代次。窗口保留调度器和原生反馈，进度状态与计算可脱离真实窗口验证。

### 启动、恢复和退出

`ApplicationLifecycleCoordinator` 集中维护启动阶段、退出阶段、初始化、关闭和已关闭状态，宿主通过 `ApplicationStartupOperations` / `ApplicationShutdownOperations` 提供具体动作。同一宿主上下文调用这些操作；没有引入跨线程修改窗口状态的新入口。

正常启动顺序：

1. 准备原生窗口，加载并应用设置。
2. 并行发现文档、光盘及硬件能力；等待硬件清单后发现媒体引擎，并等待文档和光盘发现完成。
3. 恢复主队列，再恢复压缩包任务。
4. 发布交互就绪并释放激活导入屏障。
5. 初始化自动化、核对恢复的自动化任务组，配置目录监控、安排补充服务，完成启动。

`ActivationReady` 与整个 `StartupTask` 分开：正常路径在恢复完成后允许激活导入，不必等待全部后台服务。`settings-ready` 只代表设置加载；旧 `first-interactive` 指标继续保留为设置阶段别名。真实 `add-files-ready` 要求已出现可见渲染帧、恢复完成、添加按钮和快捷操作可用，并在调度器返回后观察；托盘隐藏启动不轮询可见就绪。

退出顺序：停止压缩包 → 停止导入 → 关闭相关对话框及取消历史索引 → 停止自动化 → 等待更新偏好保存 → 停止并保存队列 → 等待启动结束。如果自动化在关闭期间才初始化，等待启动后再停止一次，防止服务在关闭后留下后台工作。保存成功后再保存窗口位置、执行退出更新安装，最后允许关闭窗口；窗口位置保存失败被记录，不替代队列保存结果。

保存失败继续使用时，恢复队列准入、清除宿主自动化停止状态并重新配置服务；选择不保存退出会再停止队列并跳过更新安装。重叠退出请求复用正在进行的操作，最终 `MarkClosed` 记录关闭并释放仍在等待的激活调用。

本轮补齐了启动恢复中断后继续使用的边界：如果任务快照已发布而探测未结束，`QueueSession` 使用新的生命周期令牌接续剩余探测，保留原任务模型、身份和顺序；如果快照未可靠发布，则重新加载。生命周期协调器重新建立激活屏障，等待主队列与压缩包恢复完成，再接续自动化和目录监控。这样不会把取消的恢复任务永久留作后续恢复结果，也不会只恢复准入标志而遗漏后台初始化。

### 媒体转换阶段

| 阶段 | 类型 | 具体责任 |
| --- | --- | --- |
| 准备 | `MediaConversionPreparation` | 选项、来源保真、输入预检、兼容解码选择、复制流准备、引擎输出能力 |
| 编码尝试 | `MediaEncodingService` | 编码器顺序、硬件解码回退、CPU 回退、目标体积搜索、ICO 帧生成 |
| 验证 | `MediaOutputValidator` | 字节限制、完整时长、尺寸、媒体有效性、动画及复制流 |
| 提交 | `MediaOutputCommitter` | 最后取消检查、提交已验证产物、发布完成进度 |

`ConversionService` 组合这四个阶段，继续拥有活动进程登记及暂停、继续和取消；`MediaConversionArtifacts` 共用私有临时产物检查与清理。预检完成后才预留输出路径，编码尝试写临时路径，验证通过后才执行 `OutputPathLease.CommitValidated` 并报告 100%。

取消不能越过提交前检查，提交冲突保留已验证产物和恢复记录。完成回调异常不能把已经提交的产物变成失败。兼容解码临时替换的来源路径、探测结果、音轨和策略选项在入口 `finally` 恢复，活动进程和取消记录也在该边界清理。独立静态审查已对照固定基线核对编码顺序、参数、取消、校验和提交语义，未发现新增行为差异。

### 可见启动与大队列核查

整理前与最终版本均完成 9/9 次真实可见启动，空队列、100 项、1,000 项各 3 次。每个样本验证窗口可见、添加按钮就绪、主队列及压缩包恢复、失败/取消/暂停状态和缺失来源保留、实际新文件导入，以及没有自动转换。

| 持久队列条目 | 整理前添加文件就绪中位数 | 最终版本添加文件就绪中位数 |

| 0 | 2.756 秒 | 2.460 秒 |

一次运行权限不同的中间测量曾得到约 38.7 秒的 1,000 项就绪中位数，伴随任务栏和通知初始化状态差异，保留作诊断记录。复核未发现重复加载或新增串行等待；同时移除了队列刷新中多余的可见条目 HashSet 扫描，改为仅检查选中身份。最终表格使用与基线相同运行权限的复测，未复现该量级的变慢。权限与扫描调整同时发生，不能把时间变化单独归因于其中一项。

### 测试 FFmpeg 崩溃弹窗

验证期间出现了 Windows 的 `ffmpeg.exe` 内存写入错误弹窗。运行进程路径确认来自 `work/ffmpeg-pruning/baseline-runtime` 的测试引擎；它与当前生产准备目录中的共享 DLL 版引擎是不同文件，版本与 SHA256 记录在 `after/ffmpeg-identities.json`。

测试进程现在在 Windows 模块初始化时保留已有错误模式并加入原生故障弹窗抑制，子进程继承该设置。原生崩溃仍返回失败退出码，测试仍断言退出结果；不让系统对话框无限阻塞无人值守验证。保留了弹窗导致的挂起、中止和定位日志；中止运行不计为通过。设置后完整测试正常结束，25 项失败仍与基线一致。这项改动仅限测试环境，不代表已修复测试引擎内部的原生崩溃。

本轮本地源码与验证结果不构成 MSIX 安装升级、商店发布或 ARM64 真机验收。
