## 检测延后决策

以下阶段取九个样本的中位数。它们存在重叠，不能相加，也不能将阶段本身的耗时直接称为优化收益。本轮保留了现有引擎检测顺序，完成基线与延后决策，没有进行延后后的 A/B 测量。

| 检测 | 阶段耗时 | 决策及边界 |
| --- | ---: | --- |
| 文档工具发现（Word/LibreOffice/Calibre/CAJ） | 543 ms | 适合移出全局恢复前的等待，后台或首次相关转换/设置页按需发现。本组 FFmpeg context 完成后到恢复开始仍有约 359–365 ms 的尾部等待，主要在等待文档发现；它比 543 ms 更接近当前关键路径上的量级，实际收益需改动后复测。 |
| 光盘工具发现（MakeMKV/cdda2wav/readom） | 136 ms | 适合首次光盘操作/设置页按需发现。本组它在 FFmpeg context 结束之前已完成，单独延后不会直接移除当前关键路径等待，主要降低启动竞争。 |
| 自动硬解实测 | 10010 ms | 适合恢复完成后、空闲或用户主动测试时开始。它当前已经 fire-and-forget，与任务恢复重叠；不能宣称延后会直接减少 10 秒启动时间。 |
| CPU/GPU 枚举 | 16 ms | 可解除与 FFmpeg 检测的串行依赖，放入后台；本机成本低，优先级较低。 |
| 硬解缓存读取 | 3 ms | 本机成本很低，不作为首要优化点。 |
| FFmpeg/FFprobe 配对验证 | 135 ms | 保留在媒体添加与媒体恢复之前；验证配对、架构与可运行性。媒体导入依赖已就绪的 ffprobe 上下文。 |
| FFmpeg 格式/解码器/编码器能力查询 | 启动未调用 | 已经在预检或转换时按需调用，无需再次延后。 |

延后文档或光盘发现时，需要保留明确的“检测中”状态，并在对应转换启动前等待发现完成；初始空字典不能被解释为最终“缺少引擎”。现有转换执行时还会重新发现对应工具，应保留执行前验证。

千任务恢复的后续优先项是继续细分 `QueueSession.RestoreCoreAsync` 的逐条导入、访问权限处理和 UI 派发，并评估将新文件导入与全量恢复门禁解耦。当前测量只定位到恢复阶段，尚无证据把约 31 秒完全归因于其中某一个子步骤。检测延后无法单独解决这个量级的等待。

## 测量口径

三个节点都从 Windows 记录的进程创建时间开始计时。应用构造时将该起点与 Stopwatch 对齐，之后使用单调时钟，不持续依赖系统时间。

| 节点 | 事件名 | 完成边界 |
| --- | --- | --- |
| 窗口出现 | `window-visible` | RootGrid 已 Loaded，AppWindow 可见，且到达首次 CompositionTarget.Rendering 回调。它是首帧绘制代理，真实 DWM 呈现需另用 ETW 跟踪。 |
| 可以添加文件 | `add-files-ready` | 初始化门禁已解除、主队列与归档恢复结束，UI 线程返回低优先级调度回调，添加按钮启用且桌面交互可用。随后实际导入新 DOCX 验证，验证耗时不计入节点。 |
| 恢复任务完成 | `recovery-complete` | 主队列和归档队列都完成恢复。自动化与其他后台服务的全部初始化不属于此节点。 |

旧的 `first-interactive` 仅表示设置应用完成；`all-restored` 仅覆盖主队列。保留它们用于兼容原有回归检查，正式交互结果采用上表的三个新节点。

应用同时提供 `FormatFactory-Startup` 自描述 ETW provider，包括三个交互的 Start/Stop、节点耗时以及各阶段事件。ETW Start 在应用构造期间发出；要从 WPA 计算进程创建到节点的完整时间，应关联系统进程创建事件或读取事件的 elapsedMilliseconds 载荷。并行阶段使用独立的名称、起点和耗时，不将它们相加推算总耗时。

## 重现方式

```powershell
pwsh -NoProfile -File tests/WinUiSmoke/Measure-Startup.ps1 `
  -RunName startup-measurement-20261028-v2 `
  -NuGetConfigPath work/feature-validation/NuGet.Config
```

每档默认三个独立进程，按 0、100、1000 项队列轮转运行。每个样本用单独的准备进程生成有效最小 DOCX 和设置，然后启动真实 App、激活可见窗口。包含一项来源缺失任务以及失败、取消、暂停状态；非空队列另含一项曾在运行的归档任务。所有样本都验证保留数量和状态、不自动转换，以及可以实际添加一个新文件。

测试宿主沿用生产启动、窗口和服务，只替换数据目录和单实例标识，关闭托盘、远程遥测和自动更新。引擎使用 `work/prepared-engines/x64/Engines`。每次启动前尽力等待 CPU 低于 5%，并保存原始 CPU 观察值；三个关键节点取样后，等待后台硬解检测结束再退出，避免干扰后续样本。

源码、构建和实测均校验指纹。每个样本保存节点原始值、阶段起点/耗时、就绪时与后台完成后的两份阶段快照；汇总使用中位数和最小/最大值，不用三次样本推算 P95。

## 适用范围

这是本机 x64 工作区的未打包测试宿主测量。每次使用新应用数据与硬解缓存，文件缓存与系统状态沿用；没有重启或清理磁盘缓存，因此不称为磁盘冷启动，也不代表已安装 MSIX 或其他设备的验收结果。有效小 DOCX 队列不代表大量音视频逐个 ffprobe 的恢复成本。

宿主日志包含通知初始化拒绝访问、任务栏方法未实现、后台注册/跳转列表失败，以及未打包身份下 Future Access List 保存权限失败。这些错误被生产代码处理，实际导入仍通过；其成本包含在样本中。尤其大队列逐条访问权限的环境与已安装 MSIX 不同，绝对值不能直接外推到已安装版本。正式结果没有绕过或模拟这些平台路径。

首次试运行使用了只支持导出的 TXT，因此实际导入检查按预期失败。该样本只保留为工具排错记录，不进入正式统计；正式样本改用目录已声明支持导入的有效 DOCX，并在准备阶段检查格式支持。
